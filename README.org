* What this is

An Org-mode benchmark lab for measuring how much model capability Prolog-RLM can substitute with symbolic state, search, recursion, and verification.

The benchmark varies:

- model capability class,
- model/provider,
- task family and difficulty,
- recursion depth,
- execution condition (vanilla, self-recursive, RLM, RLM+verification),
- token budget and trial seed.

The lab records model calls, Prolog calls, input/output tokens, latency, symbolic-runtime time, failures, endpoint identity, provider model identity, and optional API cost. Analysis generates tables, SVG plots, Org fragments, and the HTML report.

* Local inference: llama.cpp

Local inference is OpenAI-compatible and defaults to llama.cpp's =llama-server= endpoint:

#+begin_example
http://127.0.0.1:8080/v1
#+end_example

The lab does not start or configure llama.cpp. It talks to the server you already run.

Copy the environment template once:

#+begin_src sh
cp -n .env.example .env
#+end_src

If your server uses another address, set =LOCAL_OPENAI_BASE_URL=. If =/v1/models= advertises a model id different from the canonical registry name, set the matching per-model override, for example:

#+begin_example
QWEN35_4B_LOCAL_MODEL=my-loaded-model-id
#+end_example

Blank override variables do not erase registry defaults.

** Preflight

Before writing benchmark rows, the runner validates =/v1/models= and checks that the requested model is actually advertised by the endpoint. A dead endpoint or alias mismatch aborts the run instead of producing hundreds of false benchmark failures.

#+begin_src sh
make doctor MODEL_ID=qwen35-4b
#+end_src

For one end-to-end benchmark row:

#+begin_src sh
make probe MODEL_ID=qwen35-4b
#+end_src

For the smoke matrix on one model:

#+begin_src sh
make smoke MODEL_ID=qwen35-4b
#+end_src

The same raw result store can contain sessions from multiple local models, so size-class sweeps can be run model-by-model against a single llama.cpp server and analyzed together.

* Emacs / Org workflow

The primary interactive workflow remains =LAB.org=. It uses async Org Babel blocks for shell and Python execution, =ob-async= when available, and the helpers in =emacs/rlm-lab.el=.

The Emacs workflow uses the gptel backend and model already active in your running Emacs. It does not create a second provider configuration for findings generation.

The Makefile exposes the workflow as explicit tasks:

#+begin_src sh
make emacs-check   # verify the running Emacs can load gptel-request and ob-async
make lab           # open LAB.org through emacsclient
make findings      # asynchronously generate FINDINGS.org with active gptel
make report        # generate FINDINGS.org, then export REPORT.org on callback
make export        # export current REPORT.org without regenerating findings
#+end_src

=make findings= and =make report= dispatch through =emacsclient= intentionally. The callback continues in the running Emacs process, so asynchronous gptel generation is not killed by a short-lived batch Emacs process.

Inside =LAB.org= the normal flow is:

1. load =emacs/rlm-lab.el= and run =rlm-lab-setup=;
2. doctor/probe the selected inference model;
3. run smoke, recursion, and size-class experiments asynchronously;
4. analyze and generate SVG plots;
5. preview the evidence packet;
6. generate =FINDINGS.org= with =gptel-request=;
7. export =REPORT.org=, whose sections are assembled with =#+INCLUDE:=, to =public/index.html=.

* Remote / OpenRouter inference

Remote models are disabled by default. Enabling an API lane requires both:

1. setting the matching API key and exact provider model slug in =.env=, and
2. explicitly passing =--allow-paid=.

The harness never silently falls back from local inference to a paid endpoint.

Example preflight:

#+begin_src sh
python3 src/doctor.py --deployment remote --allow-paid --model-id claude-opus-5
#+end_src

Example run:

#+begin_src sh
./scripts/bench --preset frontier --deployment remote --allow-paid --model-id claude-opus-5
#+end_src

* Current model-class snapshot

The shipped model registry is a benchmark-candidate snapshot, not a permanent SOTA claim. Open-weight size classes are currently seeded with Qwen3.5 candidates because the family provides a useful parameter ladder from sub-1B through large MoE models. Closed frontier models stay in a separate class because public parameter counts are unavailable.

Edit =config/models.toml= as the model landscape changes. Analysis groups by declared class rather than hard-coding model names.

* Core metric definitions

** Capability Replacement Ratio (CRR)

For a target success threshold T:

#+begin_example
CRR = smallest vanilla parameter count reaching T
      --------------------------------------------
      smallest RLM parameter count reaching T
#+end_example

** Token Offload Ratio (TOR)

#+begin_example
TOR = 1 - (RLM model tokens / vanilla model tokens)
#+end_example

** Symbolic Work Share (SWS)

A descriptive execution metric:

#+begin_example
SWS = prolog_calls / (prolog_calls + model_calls)
#+end_example

This compares how much of the observable control loop moves into the symbolic runtime.

* Experimental fairness

The task generator owns one symbolic world. Both vanilla and RLM conditions receive the same task information. The RLM condition additionally receives access to general symbolic query machinery, not task-specific answer predicates hand-written per instance.

Every run stores its seed, provider endpoint, provider model id, and raw trace. Do not trust a benchmark result that cannot be replayed.
